# Known limits

**Reader:** people who plan fixes or need to know what the server does not guard against. Reviewed 2026-11-16.

[Index](./index.md)

**In short:** twelve surprising or fragile behaviours of today: a docs page that orders two steps the other way round, edge cases of the command line and HTTP, some couplings. Eleven are still open; row 2 was fixed on 2026-11-16 (commit c4b4a7c) and stays listed. Each says where it lives and how sure we are.

| # | Limit | Where | Status |
|---|---|---|---|
| 1 | [How it works](../how-it-works.md#one-request-end-to-end) puts "`protocol.handle` checks the era, the `_meta` and the tool" (step 2) **before** "the call waits in the worker queue" (step 3). In the code, a `tools/call` is queued raw first and `protocol.handle` runs on the worker thread (HTTP's `check_headers` runs before the queue). A request with a bad tool name waits its turn before being refused | `stdio.py:37-47`, `worker.py:72`, `protocol.py:167-169`, `http_transport.py:134-154` | Confirmed; which order the page should say is the owner's decision |
| 2 | Fixed 2026-11-16 (commit c4b4a7c). Invalid UTF-8 on stdin used to end the server: the decode error came from the `for line in sys.stdin` iterator, outside the `try` that answers `-32700`. Now stdin is read as bytes and each line is decoded on its own, so such a line gets `-32700` (`id: null`) and the server keeps serving. Test: `test_stdio_invalid_utf8_is_a_parse_error_and_the_server_keeps_serving` (`tests/test_server.py`). HTTP answers the same input the same way (`test_http_unreadable_body_is_a_parse_error`, `:1031`) | `stdio.py:29-34` | Fixed; the test came with the fix and was not run for this guide |
| 3 | Closing stdin cancels nothing: `stop_worker` queues a stop sign **after** the waiting calls and waits for the thread, so a running recording and each queued one finish first, with nobody reading the replies (they fail and are logged). The script's own watcher stops the program if the server process dies ([Recording](../recording/failures.md#what-happens-if-instruments-dies-part-way)), but a server alive with a closed stdin keeps recording | `stdio.py:57`, `worker.py:83-90` | Confirmed by the code; effect on a real client probable |
| 4 | An unknown first argument starts stdio silently, and after `--http` only `--port N` is read: `--http 9000` serves on 8765. A port the system refuses (out of range, in use) ends in a Python traceback | `metal_trace_mcp.py:88-95`, `http_transport.py:190` | Confirmed for the arguments; traceback probable |
| 5 | The `Bearer ` prefix is optional and case-sensitive: a header that is just the token passes, `bearer <token>` does not | `http_transport.py:115` | Confirmed; not run. Whether other clients send it in lower case: not verified |
| 6 | `local_host` takes what precedes the first `:`, so `localhost:1@evil.example` counts as local. A browser sends no user information in `Host` or `Origin`, so no web-page use is known; tests cover only the dotted-suffix trick | `http_transport.py:17-20`, `tests/test_server.py:317-319` | Confirmed by reading; the browser claim **not verified** |
| 7 | GET and DELETE answer 405 before the Host, Origin and token checks, so an unauthenticated client can tell the port is a server of this kind | `http_transport.py:170-174` | Confirmed (harmless: answers nothing else) |
| 8 | Only `Content-Length` is read: `Transfer-Encoding: chunked` is read as an empty body and answered 400 `-32700` | `http_transport.py:125-133` | Probable: not run |
| 9 | An old-era HTTP call has no timeout of its own: the tool sets the length. Only a recording has a deadline (15 s per recorded second plus 180, [Recording](../recording/index.md)) | `http_transport.py:160-161` | Probable |
| 10 | Three spellings: the startup refusal prints `metal-gpu-trace:` (`:188`, outside `logs`, not silenced by `METAL_TRACE_LOG=off`), log lines print `metal-trace:`, and `serverInfo` says `metal-trace`. `logs.py`'s docstring and the README say one line per call; the code writes seven kinds | `http_transport.py:188`, `logs.py:1`, `:9`, `protocol.py:78` | Confirmed (cosmetic) |
| 11 | `worker._send` is `stdio.send` also under `--http` (`metal_trace_mcp.py:50`). Progress is safe only because the HTTP handler removes `progressToken` first; without that, progress would go to stdout, where no client reads it | `metal_trace_mcp.py:50`, `http_transport.py:145-151`, `worker.py:149-151` | Confirmed (coupling, not a bug today) |
| 12 | `worker.call` turns `FileNotFoundError`, `ValueError` and `RuntimeError` into the client's text with `str(error)`. The README's "no path in an error" rule holds because each tool uses `ToolError` with its own wording, not because of the worker; a raw `FileNotFoundError` from a new tool would show its path | `worker.py:165-166` | Probable: no tool does it today |
