# Proof for 0.29.0

**Reader:** people

Each improvement below was run on the code of this release, on 2026-11-22 (see [docs/evidence/README.md](README.md) for how a proof
is read). The recordings are real: two 12 s recordings in native Metal on Apple silicon, `vsync-cubes` (bgfx example
`01-cubes`, locked to the display) and `cpu-bound-draws` (`drawstress`, `dim=40`), each with its `.json`, frame and
memory CSVs and `.tables.sqlite`. The "before" outputs come from the code of the `v0.28.0` tag run on those same
summaries. Paths and machine names are left out of every output.

**Where and when (macOS):** macOS 27.2.1, Apple M1 Pro, Xcode 27.2; 2026-11-22.
**Where and when (Windows):** Windows PC, Python 3.12.14, PresentMon installed; 2026-11-22.

## perf_diagnose tells a display-locked run from a CPU-bound one

**Promise:** when the GPU is idle a lot but the run is locked to the display (`display_synced_hz` is set),
`perf_diagnose` answers `DISPLAY_SYNCED` instead of `CPU_SUBMISSION_BOUND`; a run that is really CPU bound keeps its
verdict; the recommendations are in English.

**Command:** `analysis.tool_perf_diagnose(<run>)` of the `v0.28.0` code and of this code, over the same two real
summaries (`METAL_TRACE_OUT` set to their folder).

**Output:**

```
0.28.0
cpu-bound-draws {"bottleneck": "CPU_SUBMISSION_BOUND", "display_synced_hz": null, "fps": 102.4} | Consolidar draw calls mediante instancing o reducir complejidad ...
vsync-cubes     {"bottleneck": "CPU_SUBMISSION_BOUND", "display_synced_hz": 120,  "fps": 120.0} | Consolidar draw calls mediante instancing o reducir complejidad ...

0.29.0
cpu-bound-draws {"bottleneck": "CPU_SUBMISSION_BOUND", "display_synced_hz": null, "fps": 102.4} | Merge draw calls with instancing, or reduce geometry complexity and dynamic objects.
vsync-cubes     {"bottleneck": "DISPLAY_SYNCED",       "display_synced_hz": 120,  "fps": 120.0} | The FPS (120.0) matches a 120 Hz display and the intervals are regular: probably vsync; th...
```

The display-locked run (120.0 fps on a 120 Hz display) was told to merge draw calls before; now it is told it is waiting
for the display. The CPU-bound run (102.4 fps) keeps its verdict.

**Not tested:** a display-locked run at a refresh rate other than 120 Hz; a variable-refresh display.

## A summary is written atomically

**Promise:** a recording's `.json` is written through a unique temporary file in the same folder, flushed to disk and
renamed over the previous one, so a crash or a full disk leaves the old file or none, never half a file; a link as
destination is refused; the file mode still follows the umask; errors name the reason, not the path.

**Command:** `python3 -I tests/run.py test_paths` (a SIGKILL in the middle of a write, a link, a folder without
permission, a full disk, the umask mode), then the two real summaries above, read back.

**Output:**

```
8 tests ok
ok

vsync-cubes_20261122-180721.json       schema_version 3, common block present, 8468 bytes, mode -rw-r--r--
cpu-bound-draws_20261122-180811.json   schema_version 3, common block present, 7733 bytes, mode -rw-r--r--
(no .tmp file left in the folder)
```

**Not tested:** a real power cut; Windows with the destination open in another process (`os.replace` can fail there and
surfaces as a `ToolError`; noted in `docs/guides/data-and-lifecycle/limits.md`).

## The device block says why a hardware daemon gave no answer

**Promise:** on Windows, when a hardware daemon is found but gives no usable answer, `device.daemon_info_error` is
`timeout`, `invalid_json` or `missing`, never a path; no daemon at all is not an error.

**Command:** `python3 -I tests/run.py test_recording` (the case `device["daemon_info_error"] == reason` for each
reason, a good answer with no error, and no daemon).

**Output:**

```
88 tests ok
ok
```

**Not tested:** a real VegaFlow daemon that times out or answers broken JSON (the tests use a fake one).
