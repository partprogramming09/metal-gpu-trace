## trace_query with window_ms

**Promise:** `trace_query` with `window_ms` returns time windows (`count` and summed duration, in the `rows` page) instead of rows, so a
table of tens of thousands of rows is summarized without cutting off its middle.

**Command:** `trace_query` on a kept `.trace` of a Wine run of a test program (the `mullion` project), table
`metal-gpu-intervals`, with `window_ms=1000` and `limit=3` (run again on 2026-11-15 after the review fixes); then the same call on `time-profile`; then without
`window_ms` to count the rows.

**Output:**

```
metal-gpu-intervals  total=31 windows, window_ms=1000, next_offset=3
  {"start_ms": 0,    "count": 14, "duration_ms": 21.162}
  {"start_ms": 1000, "count": 18, "duration_ms": 27.29}
  {"start_ms": 2000, "count": 907, "duration_ms": 116.869}
time-profile         total=28 windows, window_ms=1000
  {"start_ms": 0,    "count": 62}
  {"start_ms": 1000, "count": 44}
  {"start_ms": 2000, "count": 433}
metal-gpu-intervals without window_ms: total=19710 rows
```

19 710 rows of `metal-gpu-intervals` became 31 windows of 1 s. `time-profile` has no duration column, so its windows carry
only `count`.

**Where and when:** macOS 27.0.1, Apple M1 Pro, xctrace 27.2 (27B52); 2026-11-15. The trace was recorded on 2026-10-18.

**Not tested:** `window_ms` with `pid` on a real trace (covered by a synthetic test only); a `.trace` from a native Metal run (only one from a Wine run); tables other than these two; the
`metal-gpu-counter-intervals` table.

## Run context: commit and Instruments version

**Promise:** every new run's summary carries `context` (the short commit and dirty flag of the project's repository, and Instruments' version), and `perf_compare` says in `context` whether two runs share it, so a baseline can be tied to the code it measured. No branch, path, user or machine name.

**Command (run again after the review fixes):** `run_context()` with a project file at the repository root, then without a project file.

**Output:**

```
with a project file:    {"git": {"commit": "83d92374d708", "dirty": true}, "instruments": "27.2 (27B52)"}
without a project file: {"git": null, "instruments": "27.2 (27B52)"}
```

`dirty` was true because the changes of this very improvement were not committed yet. `perf_compare` returns `context` as `{"same": true}`, `{"same": false, "a": ..., "b": ...}` or `{"missing_in": [...]}` for runs recorded before 0.26.0 (covered by tests with stored summaries); `same` is `null` with `unknown_in` when a run's commit is unknown.

**Where and when:** macOS 27.0.1, Apple M1 Pro, xctrace 27.2 (27B52), git on this checkout; 2026-11-15.

**A whole recording:** `perf_record` through the MCP server on `drawstress` (`api=mtl`, `seconds=30`, native), with a project file at the root of a throwaway git repository (one commit, clean tracked files). The saved summary of that run holds:

```
"context": {"git": {"commit": "3fad93bf1c4a", "dirty": false}, "instruments": "27.2 (27B52)"}
```

The run itself: 454 frames, 100.8 FPS estimate, 30.9 s. Its window stopped presenting after 6.7 s (`unpresented`, 84 % of GPU time), so that run is good as proof of `context`, not as a performance measurement. Recorded on 2026-11-15, same machine and tools as above.

**Not tested:** Windows; a `perf_record` of a Wine program (the recording above is native).

## The diagnose-stutter prompt

**Promise:** the prompt gives the agent the order `perf_cold_warm`, then its fields, then `perf_diagnose`, quoting only fields those tools return.

**Command:** `perf_cold_warm` on `drawstress` (`api=mtl`, `seconds=20`; the prompt says `seconds=30` and passes `api`, `mtl` unless the caller gives another), then `perf_diagnose` on the second run.

**Output:**

```
first : 2045 frames, 6 hitches {cpu_or_wait: 5, memory_growth: 1}, compiler_busy_ms 0.227
second:  153 frames, 4 hitches {cpu_or_wait: 3, memory_growth: 1}, compiler_busy_ms 0.292
first_seen_hitches 0, extra_hitches_in_first 2
perf_diagnose(second): too_short false, unpresented {frames 160, from_s 3.637, span_s 17.236, share_of_gpu_time 0.92}
```

The chain ran and every field the prompt names exists. The second run is **not a valid diagnosis**: its window stopped presenting for 17 s of 20, which `perf_diagnose` reports as `unpresented`. The prompt now says to record such a run again with the window visible (a test pins that sentence). This is why the improvement is marked 🧪.

**Again, with both windows visible (2026-11-15, later):** the same chain on the merged code (`seconds=20`, `tier=light`, 151 s in all):

```
first : 1760 frames, 1 hitch {cpu_or_wait: 1}, compiler_busy_ms 0.24, unpresented none
second: 1755 frames, 2 hitches {gpu_heavy: 1, cpu_or_wait: 1}, compiler_busy_ms 0.256, unpresented none
first_seen_hitches 0, extra_hitches_in_first 0
perf_diagnose(second): too_short false, unpresented none, suggested_actions []
```

This pair is a valid diagnosis and every field the prompt names exists. `drawstress` builds its pipelines before it starts presenting, so the case the prompt exists for (`first_seen_hitches` above 0) did not occur: the improvement stays 🧪.

**Where and when:** macOS 27.0.1, Apple M1 Pro, xctrace 27.2 (27B52); 2026-11-15.

**Not tested:** a program that does build pipelines during the run (`first_seen_hitches` above 0); a Wine run.

## The bisect-regression prompt

**Promise:** the prompt orders `git bisect`, a recording and a check per step, and a repeat before each mark; the server runs no command.

**Command:** none yet. Covered by tests of the text, of the arguments (`;`, `$(`, spaces, `/`, a leading `-` are refused) and of the tool names it uses.

**Not tested:** following the text on a disposable repository with commits that change a `drawstress` argument, to see `git bisect` name the right commit. Until then the improvement is 🧪.

## capture_diff compares two captures

**Promise:** `capture_diff` says which Metal calls a change added or removed, overall and per debug group, from two `.gputrace` captures and without Xcode.

**Command:** `gputrace_read.diff` on two synthetic MTSP streams (`test_diff_of_the_example_in_the_evidence` in `tests/test_capture.py` builds this exact pair): `before` has groups `shadow` (1 draw) and `main` (1 pipeline, 2 draws); `after` has `main` (1 pipeline, 4 draws) and `shadow` (1 draw), in the other order.

**Output:**

```
aligned_by: debug_group
totals: drawPrimitives {a: 3, b: 5, delta: 2}, setRenderPipelineState {a: 1, b: 1, delta: 0}
groups: [{name: main, a: {drawPrimitives: 2}, b: {drawPrimitives: 4}}]
```

`shadow` is not listed: it did not change, and the order of the groups did not matter.

**Where and when:** macOS 27.0.1, Apple M1 Pro; 2026-11-15.

**Not tested:** two real captures made by Xcode (none was on this Mac), so the call ids are those already in `gputrace_read.CALLS` and a real `drawstress` capture may use other draw overloads (indexed, indirect, mesh) that are not counted. This is why the improvement is 🧪: it is proven on synthetic streams only.
